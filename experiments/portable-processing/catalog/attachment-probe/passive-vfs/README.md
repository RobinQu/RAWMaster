# Observing live SQLite WAL and SHM attachments on macOS

A generated fixture and an isolated single-connection native worker exercise Apple SQLite through a named forwarding VFS. The worker opens only the fixture. The observer forwards each SQLite call to the system unix VFS and records metadata. The controller is a separate OS process. It pins its own independent file descriptors and controls the requested filename exchanges while the worker waits at pipe barriers.

## Evidence

The strengthened run passed 14 cases and 28 in-transaction observations on APFS and macOS 27.0.1 arm64. The native worker and independent keeper both used Apple SQLite 3.54.0. The actual main descriptor agreed with the trusted pin, current name, and the external process inspector in all 28 observations. The WAL had a live physical witness in 26 observations, including the two exclusive-mode observations. The SHM mapping had one in 24. Eleven decisions accepted the expected live attachments and seventeen rejected substitutions or unsupported storage. All 28 comparisons covered the hashes and sizes of both the live and peer directories' main, WAL and SHM. All 14 runs restored the exact opened set before SQLite teardown. The raw strengthened receipt SHA-256 is 3e5aaf33afa6e5b6fc7ba083791bfb87d2d0ca047a40c33228169ebb4d0b1ea2.

The preserved first run also passed 14 cases. Its worker used system SQLite 3.54.0 and its independent Python setup connection used SQLite 3.49.1. The first run measured the current names before and after each observation. Its receipt SHA-256 is d851690e3bb347f37e9549e8f962eb0401730d2634268b79bc388c01ef5e5c7d.

- Four ordinary cases used a real read transaction or BEGIN IMMEDIATE, each with an empty or uncheckpointed WAL.
- Eight cases exchanged the WAL, the SHM, or both. They cover replacement before opening, after the first in-transaction observation, and returning the trusted names after SQLite attached the duplicates. The main file remained in place. Replacements started byte-identical with different inodes.
- Under normal dirty WAL, SQLite naturally read a WAL frame and held shared mask 16 at both observations. A zero-byte WAL produced zero WAL reads and shared mask 8. BEGIN IMMEDIATE additionally held exclusive mask 1.
- Two negative cases used exclusive heap WAL-index mode and the rollback journal. The former had a plausible 32 KiB SHM file next to the database and a verified empty WAL, while SQLite made zero SHM maps and held zero SHM locks. The latter exposed no WAL open or SHM map. Both denied attachment authority.

## Capture and ownership

The worker uses sqlite3_database_file_object only within the native WAL xOpen callback. It checks the resulting main-wrapper association and the journal pointer for the same connection in the actual transaction. Within the synchronous forwarded xOpen, a process-local reversible testing hook calls SQLite's saved native open function and immediately obtains the returned descriptor's vnode. An independent before/after process descriptor inventory must show exactly one additional surviving regular descriptor. The descriptor remains owned by SQLite. The controller independently asks the Darwin kernel for that specific worker descriptor and its live vnode. The optional VFS testing hook is gated before the suite; a missing or ambiguous fd has no WAL authority.

For the SHM, the worker retains a borrowed region address only after SQLite itself successfully obtains non-null page zero. It records the original native map, successful lock and unlock operations, and invalidation at native unmap or close. During the real transaction both processes query the Darwin kernel for the exact pointer's full 32 KiB file-backed region, at file offset zero. The checker never dereferences or separately unmaps the region. The worker tracks shared read slots and requires an exclusive writer slot during the write transaction. An unsupported or heap mapping cannot produce SHM authority. Both proofs compare device, inode and nanosecond birth to the trusted held file and the current filesystem name. No diagnostic opens, locks, truncates or extends a WAL or SHM file in the SQLite process.

All file exchanges occur in generated temporary directories. The controller restores the names SQLite actually opened before rollback and close, then restores the original fixture layout and releases the keeper for normal shutdown. A separate immutable read verifies writer, marker and quick_check. A normal read may legitimately initialize or recover an SHM, and the setup connection may checkpoint on shutdown. Per-observation byte checks are therefore confined to the controller barriers. A pair of individual WAL and SHM exchanges while the worker is paused does not model a system-wide atomic rename of two independent files.

## Reproduction and limits

From this directory, run \`/usr/bin/python3 run.py --output verified-14-cases.json\`. Apple clang builds the shim, the optional hook gate and the inspector against public SDK headers. Pass \`--no-build\` for an existing matching build. Receipts include the Apple source ID, observed system calls, transaction states, lock masks, independent identities, both observations and teardown results. Raw process addresses serve only as parent/child IPC and are omitted from stored receipts.

This experiment witnesses current live attachments on the tested local system unix VFS under real SQLite transactions. Trust comes from independent fixture pins established before the controlled exchanges. It cannot classify an equal-byte replacement that already existed before that baseline, a swap after the last observation, other VFS implementations, or genuine offline media. The process-global optional native syscall override is limited to its own test worker. Production integration and timing were outside this experiment.
