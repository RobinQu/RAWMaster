# 中断后继续一批成片交付

摄影师可以从「导出 → 任务详情」进入当前交付，也可以从「制作任务 → 查看详情 → 查看本批交付」打开之前提交的批次。两处使用同一批次号。工作台中的当前选片、焦点、采用版本和新设置独立于这份回执。[摄影工作台](../../docs/ui/prototype/index.html#export) · [制作任务](../../docs/ui/prototype/index.html#jobs) · [三张照片独立样本](prototype.html)

提交时保存有序的照片与版本、来源内容身份、实际配方、输出设置、渲染日期、目标目录身份与访问凭据、字面文件名和重名策略。名字中已有的句点、原序号和按提交日期展开的内容都会保留。每张照片有独立的准备与交付记录。新进程打开回执先核对结果，用户点「继续未完成项」后才开始写入。关闭详情、返回资料库或编辑可保留当前操作位置。

| 任务详情中的状态 | 可以做什么 |
| --- | --- |
| 已核验 | 查看本批文件名、来源和提交时的版本。后续继续时保留这项结果。 |
| 交付已中断 | 核对原目标后，点「继续未完成项」。已写出但还未来得及确认的文件，在准备票据与目标文件核对通过时计入已核验。 |
| 目标目录离线 | 在任务内点「接回原目标目录」授权当前所选位置。工作台以提交时的卷身份和目录身份核对。相同路径指向另一卷或另一目录时，保留离线状态、已发布文件和原票据，焦点留在接回按钮。原卷重挂后，即使系统设备号已变，同一目录仍可核对。待核验文件先按票据认领，焦点移到可用的继续操作，用户明确继续后才写余项。面板上的目录选择只影响新提交。 |
| 原片待找回 | 在该行「接回原片」。冻结版本已有可用归档的照片可以独立完成。接回后再点击继续，沿用原序号。 |
| 写入失败 | 已成功项可查。摄影师修复原因，再点「重试未完成项」。 |
| 同名文件待核对 | 等待核对原目录。已准备项绑定到具体文件与路径，同名同内容的外来文件也会保留并显示冲突。未准备项第一次发布时使用冻结的重名策略和字面基名，可以跳过或取得安全后缀。最终目标使用排他发布。 |
| 已取消本批交付 | 停止余项并保留回执与已有文件。重新打开仍显示已取消。摄影师可以在导出面板发起新的批次。 |

详情逐项显示原照片、版本、输出名和状态，并给出已核验与待处理计数。没有可继续的项时，主操作禁用并显示原因。按 Escape 或「返回面板」关闭详情，焦点回到「任务详情」。原型的「模拟中断与故障」用于复现进程中断、目标掉线、单项写入失败，以及内容相同但身份不同的占位文件。

## 走查

1. 在三张样本中选择「网络分享」，模板使用 `{name}.v2-{index}`，提交后等待第一项已核验。展开「模拟中断与故障」并选择「模拟退出并重开」。核对第一项、第二项及离线项仍带提交时的序号和版本。直接刷新页面也可以触发恢复。
2. 关闭详情，到资料库改选另一张、到编辑查看另一版本，再从「制作任务」打开原回执。确认当前选片独立，继续后只增加余项。原片离线时在对应行接回，准备好后明确继续。
3. 在另一批部分完成时断开目标目录。刷新，并尝试改变面板上的目标目录。回到详情仍只允许接回原目录。确认第一项后模拟一次写入失败，显式重试并检查已核验文件名及票据仍相同。
4. 在待核验的间隙重开，同一准备票据可确认已写出的结果。再用新批次在一项处理中模拟同名占位，核对外来文件不会作为成功项。模拟占位文件由外部移走后，重新核对并继续原项。
5. 在另一批完成第一项后取消，重新打开后检查其终态、已有文件和键盘焦点。另行提交应产生独立的批次。浅色、深色及窄窗均可读取状态、逐项找回和操作主按钮。
6. 从「制作任务 → 查看详情 → 查看本批交付」打开断开目标的回执。展开「模拟中断与故障」，选择「同路径挂载另一卷」。用键盘按下「接回原目标目录」，确认仍显示「目标目录离线」和「接回提交时使用的输出目录，然后继续。」继续按钮保持禁用，焦点留在接回按钮。模拟区可查看卷身份不同的原因。刷新后再次打开原回执，原文件名和票据仍在。
7. 在同一回执中选「原卷以新设备号重挂」。用「接回原目标目录」核对，检查先前已发布待核验的那一项成功认领。停留在详情时余项数量不变，点「继续未完成项」才开始交付。用 Escape 返回，再回到资料库，确认改选后的照片和焦点仍在。[任务入口](../../docs/ui/prototype/index.html#jobs) · [独立样本](prototype.html)

浏览器在本机模拟并记录批次回执和目标目录中的文件身份。原生验收需要进程退出后重新启动、实际输出 SHA-256、对预备文件的身份核验、取消期间留下的文件、离线卷及已变化的来源。[Spec 035 验收矩阵](../035-portable-processing-cores/acceptance.md)

## 原生复验

使用原生工作台提交三张照片，命名模板为 `{name}.edit-{index}`。第一张实际交付后，在第二张出票前、出票后和排他发布后待确认三个时点分别向当次 XCTest 进程发送 SIGKILL。三个新进程读取同一批次，切到资料库选中另一张照片，并从原回执确认和继续。三组均保留第一份成片的文件身份和摘要，顺序、版本和当前选片不变。发布后待确认的第二张仍保有原文件身份。每次都拒绝以新建同名目录替代原目录。最后一组移动第三张源文件，先用另一照片验证拒绝，再以冻结源的相同字节接回。九个最终成片按路径和 SHA 与 Rust 票据独立核对。[原生用例](../../Tests/RAWMasterUITests/WorkbenchContinuation035Tests.swift) · [跨进程验收命令](../035-portable-processing-cores/verify-workbench-restart.py) · [实际回执](../035-portable-processing-cores/evidence/workbench-native-restart.json)

随后分别以普通内联清单和含草稿编辑的资源清单重放三种进程中断。接回的第三张改名为不同扩展名，原始解码类型与实际源摘要均保持。六次重启都有原进程的暂存文件或票据与恢复成片的 SHA 对照。两份编辑备份的恢复副本均只读显示批次历史。独立复跑全尺寸 JPEG 的间歇性编码前像素差另有记录。[两类冻结输入与恢复回执](../035-portable-processing-cores/evidence/workbench-native-restart.json) · [全尺寸重渲染精度记录](../035-portable-processing-cores/evidence/workbench-restart-advanced-precision.json)

v10 在私有 APFS 镜像上用相同原生入口另验五种情况。原卷改号、改号并换挂载路径，以及资料库所在卷随目标一起改号，都能重新授权并继续余项。另一卷使用原路径和相同成片字节时被拒绝。已发布文件保持原身份，待发布项沿用原票据；原进程退出后录入的其他选片保留。v9 记录升级后只有保留原设备号的对照成功续接。[卷、目录身份和逐项成片](../035-portable-processing-cores/evidence/workbench-apfs-remount-batch13s.json)
