# 技术计划草案

状态：2026-10-23 用户已确认 09 的 D02 / D03 / D04；方案审查通过，开始 A 阶段。下述设计的实现与验证状态另行记录。

## 1. 沿用基础，集中改动

继续采用 SwiftUI + AppKit、系统 SQLite、ImageIO / Core Image。不新增数据库/同步框架，不引入后台守护进程。新增本地偏好、文件位置、组与建议状态的清楚边界；稳定业务身份和变更记录继续为 M3 保留。

当前已知问题是设计输入而非本轮修复：根视图固定 `.dark`；画布/面板为全局固定色；有多处黑色叠层；无设置 Scene；当前图标只有原生系统变体。`AssetRecord` 不保留时间精度和原始时间语义；`LibraryStore` 打开时直接设置 `user_version=1`，新增模型前必须替换为真实版本迁移。现有合并对成员参与状态使用 OR，下一批不能沿用其作为冲突交互。

## 2. 外观解析与呈现

一个本机 `AppearancePreference` 保存 system / light / dark，单一解析结果供所有窗口与图标消费者使用。system 从 AppKit 有效外观读取，包括高对比浅/深映射；手动档不被系统事件改写。启动先读偏好再显示窗口，避免先亮后暗；偏好未知值回退 system，保留正确的设置说明。

用语义色表定义应用背景、画布、面板、边界、主要/次要文字、选择、状态及叠层。原生文本/材质优先，必须自绘处才指定两套颜色。照片画布随主题使用中性灰，不增加独立画布开关；图片解码无主题输入。错误和选择不能仅依颜色区分。

设置用独立 SwiftUI Settings Scene；现有工作台、新窗口、表单和关于窗口消费同一偏好。AppKit 图像视图仅更新容器背景，不重建图像管线或清空缓存。

为手动浅/深档准备由原生 `.icon` 导出的系统裁切图案，作为运行中 Dock 图标；system 档清除临时 Dock 覆盖，回到原生系统资源。回到 system 时不可遗留上一手动图标。公开 API 与系统染色模式的组合需先在本机验证；无法满足时回到审阅，不用私有 API 或改应用包绕过。

设置偏好按本机存储，不入 SQLite 领域日志。UI 外观事件只触发主题消费者更新，不调用全库 reload、重新选择照片或重新解码。

## 3. 重新定位：证据先于写路径

拟新增 RelocationService，分扫描/核验、计划审阅、提交三个阶段。只在用户选定根下解析合法文件，不跟随越界符号链接。先按保存的相对路径定位，失败时再用文件大小等廉价条件缩小候选，最终完整 SHA256 决定身份。

应用日志中的 hash 是匹配依据；没有旧哈希不能在源已丢失后自创身份。新路径与原有有效路径的关系、多个同内容候选、来源根与受管根不同角色都进入报告。扫描不写资产的当前位置；确认时复核内容、路径角色及记录版本，再在短事务中更新匹配项及操作记录。

重定位会话可保存进度，但缓存核验不等于永久可信；恢复或提交前检查当前文件，变化则重新完整核验。大文件哈希在数据库锁之外，不能阻塞选片写入。提交通过路径/内容变化消息使相应图像请求失效；未改变的照片缓存不动。旧请求的晚返回不得写回新位置状态。

会话历史来源是不可变来源信息；继续接入使用单独的当前源根。受管根移动需同时记录新的有效受管位置与继续写入目的地，不修改原始来源。未重新定位的记录保留各自路径，报告部分完成。目的地仍受 FileSafety 约束。

目前注册去重依赖 `(session_id, source_path)`。源根改变后不能直接拿新路径再次注册，否则会重复创建已有资产；恢复扫描需以稳定会话、相对路径和内容身份查找既有记录，内容不同时保持 changed / 新内容审阅语义。读取源文件统一解析有效源位置；原始来源只用于溯源，不能继续被读取逻辑当成唯一可读路径。导出保护同时纳入有效位置，避免重定位后误选源目录为交付目的地。

## 4. 组命令与恢复

将新增与已有组修改统一为领域命令，携带预期版本、before/after 与影响实体集合。状态写入、组版本和操作记录同一事务提交。先做拆分、类型纠正、锁定及已有入口的恢复，再接候选确认；候选不得直接调用会覆盖人工结果的旧路径。

保存最小变更，成员恢复不带走照片的后来决定/评分。现有资产级 revision 会因评分而变化，不能据此把所有后续评分都当组冲突；增加组结构/成员域的版本或等效依赖指纹。不同成员域操作是否冲突按实际修改集合判断。

⌘Z 按当前运行实际命令顺序撤销；重启后的“最近组操作”只恢复持久组命令，本批不冒充已有完整跨次运行选择历史。补偿前检查后续相关命令与预期组版本；冲突只报告，不覆盖。独立照片决定仍使用原有契约，不被候选评分取代。

## 5. 连拍候选计算

先补非破坏元数据再计算：保留原始时间、亚秒与偏移；没有偏移的本地拍摄时间不转换为伪精确 UTC，时间精度不足不做确定性时序。只在已确认同源相机的范围内比较，相机机型相同不等于同一设备。

计算链：固定输入快照 → 保守时间候选 → 有上限的预览特征 → 相邻边界判断 → 可解释候选。候选数量/成员上限、时间与相似阈值写入算法参数，不硬编码成所有机型通用常识。时间窗、链式相似造成跨场景漂移需专项测试；过长组分段展示，并提示边界需人工确认。

预览特征首选系统 Accelerate / vImage 或已有图像框架的轻量方案，不引入大模型。具体距离函数在获批后的技术验证比较误并/漏分及运行成本后冻结。缩略图方向归一、颜色/曝光变化鲁棒性、相同场景独立拍摄等都要验证；阈值只能来自开发集，留出集不用于反复调参。

建议记录包含 scope / 输入内容与元数据版本 / 参数 / 算法版本。人工评分不改变图像特征输入；组操作会使依赖组结构的候选过期。用户确认时复核输入与组版本，不能把迟到结果覆盖当前状态。

## 6. 调度与资源

新增任务只低优先级读元数据/预览，不自动读取整批完整 RAW。前台当前照片/比较请求优先；最多一个候选工作单元在执行，分块检查取消。降低任务优先级本身不能保证前台优先，必须避免后台大量请求占据现有解码许可队列。

复用已缓存预览，后台缺图按小批拉取，前台发生请求时停止投递下一后台单元。不可中断的单次读取需记录最大阻塞时间；超预算就降低预览尺寸或在活跃交互期间暂停投递。哈希扫描另有上限，不能与复制/导出多路争抢磁盘。暂停/恢复不重新计算已提交且输入未变的候选。

沿用现有预览/细节缓存预算；拟定额外候选特征内存上限 64 MiB，重定位扫描内存上限 32 MiB（不含既有图库快照与系统缓存）。这些是实现预算，不是已测结果；真正 RAW 峰值保持单独记录，不把两类内存混算。若 3 万张试验暴露全量图库快照或逐资产查询成本，先按当前作用域批量读取，不能在主线程再加全库循环。

## 7. 验证与数据迁移

先建立 schema v1 的固定测试库及升级/失败/新版本拒绝矩阵。迁移前用 SQLite 一致快照能力备份，不能单拷活动 WAL 主文件；保存备份路径及兼容说明。显式事务升级 schema 版本，新字段有可控缺省。未知更高版本不写入，失败保留原库与备份。仅备份元数据不声称原片已备份。

测试沿用现有正确性与性能入口，加双主题、重定位和组命令组合测试；新故事的故障场景见 spec。真实 RAW 均只读，破坏性文件故障只用测试副本或注入，不要求拔用户工作盘。

性能分三种负载：无后台、候选运行、重定位哈希运行；沿用 002 的输入/视图更新/解码/画布门槛及同机前一基线，不能将异常新基线重新归零。主题切换不发生解码是独立断言。导入/导出并发控制按当前互斥约束记录，不宣称已经支持任意并发组合。

分组质量先请求用户确认一小批连拍边界作为开发集，再冻结规则，用不重叠的真实组/拍摄片段留出评估；不能随机拆相邻帧导致同组泄漏。真实数据不足就报告阻塞的 B2 验收，不影响 A/B1 独立交付。A7R5 / Q3 及特殊用途必须有对应样本才进入支持清单。

## 8. 方案冻结时的研究结论与未验证项

- 已从工程确认：固定深色、元数据粒度、schema 版本设置、组操作和性能入口均符合上述现状；没有执行新技术实验。
- 已从 Apple 官方文档及本地 SDK 核对：AppKit effectiveAppearance / appearance、Dock applicationIconImage；原生 `.icon` 已有两套变体。全系统位置按应用手动主题强制变化不可据此承诺。
- 获批后需验证：Dock 图标与系统样式组合、设置窗口一致性、实际时间元数据可用性、分组规则质量、后台调度及迁移恢复。
- 数据库继续 SQLite；Automerge 独立实验不升级成运行时依赖。本批不涉及网络契约，不创建无实际用途的服务端接口。
