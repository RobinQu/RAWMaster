# 041 · Server 图像编辑模块

2026-11-27 · **规划中，未开始实现。** 本文把 Server 图像编辑收窄为**非交互批处理**：客户端负责全部交互编辑；Server 负责编辑代理生成、最终／批量渲染、重计算和 Flux 等生成式任务。不做 Server 交互预览，不做客户端与 Server 同请求并行渲染。

Server 图像模块是资料库 Server 的可选能力：资料库基础始终可用；图像模块需要兼容 CUDA 的 NVIDIA GPU 作为硬件准入，实际影像渲染和计算使用 Vulkan 后端；生成式模型使用 CUDA AI 推理栈。客户端队列和 Server 队列的详细语义见 [queues.md](queues.md)，技术方案见 [plan.md](plan.md)，任务见 [tasks.md](tasks.md)。

## 1. 结论

1. **交互只在客户端。** 滑杆、曲线、蒙版、裁切、撤销、历史、版本采用都不经过 Server。任何网络环境下都不做 Server 交互渲染。
2. **Server 只做批处理。** 编辑代理生成、final/batch render、heavy AI、Flux 等生成任务进入 Server 队列；结果异步返回，作为候选或派生资源。
3. **高质量可交互代理。** `editProxy` 尽量保持原生或高分辨率、10-bit 广色域、高质量编码；本地交互按视口渲染，松手后按代理分辨率出帧；1:1、最终和导出使用原件。
4. **最终输出必须过色彩门。** Server final 与本地最终不得有可见差异；色彩管理以独立色彩规格为准。未过门前，Server final 只能作为候选／诊断，不自动采用。
5. **CUDA GPU 是硬件准入，Vulkan 是影像 API。** Server 图像模块要求 NVIDIA CUDA GPU；`rawmaster-image` 在 Linux 使用 Vulkan；生成式模型使用 CUDA AI 栈。
6. **队列是两边各自持久化的。** 客户端 SQLite 背景队列；Server PostgreSQL 作业队列。两边通过 gRPC 提交、查询、取消、重试和结果取回协同，不共享队列数据库，不要求两边同时在线。
7. **资料库与图像能力解耦。** 没有 GPU 的 Server 仍完整提供归档、取回、元数据和恢复；客户端隐藏图像批处理入口，不静默降级。

## 2. 用户故事

### US1 · 云端存储无感（P0）

摄影师打开一张只有显示代理的照片。资料库先显示代理；进入编辑前，客户端后台取回或生成高质量 `editProxy`，到达后平滑替换；本地交互保持响应。离线或网络慢时明确显示可用级别，不阻塞已有缓存照片。

**独立验收。** displayProxy 立即可看；editProxy 后台准备；进入编辑不出现空白；代理替换不改变选片／编辑上下文；1:1 和最终使用原件或明确提示。

### US2 · 本地交互不受 Server 影响（P0）

Server 在线或离线都不改变本地滑杆、曲线、蒙版、裁切和撤销的响应。Server 队列只显示后台状态，不阻塞画布；用户可继续编辑、换片或退出。

**独立验收。** 断开 Server 后本地编辑继续；后台任务排队／重试不影响前台帧；Server 结果迟到不会覆盖当前编辑。

### US3 · 批处理最终渲染（P0）

用户对一张或多张照片提交 final/batch render。作业冻结输入、配方、引擎和输出；客户端可关闭窗口；结果稍后出现为候选，用户明确采用或导出。

**独立验收。** 同一作业重试只登记一份结果；旧输入／配方结果标过期；Server 失败不丢本地编辑；色彩门未过时不自动采用。

### US4 · 生成式任务（P1）

用户提交 Flux 等生成任务；Server 使用 CUDA 栈执行，`rawmaster-image` 负责输入准备、色彩、蒙版、合成和后处理；结果作为候选，需显式采用。

**独立验收。** 缺 CUDA／模型／显存时明确禁用；生成结果绑定输入和模型版本；取消／失败／重试可清理；不自动覆盖当前版本。

### US5 · 队列可见、可取消、可恢复（P0）

用户能看到客户端背景任务和 Server 作业的状态、队列位置、取消和重试。关闭窗口、断网、重启后任务不丢失；不确定结果先核对，不重复提交。

**独立验收。** 客户端重启恢复本地任务；Server 重启后作业可续／重试；重复提交同 ID 只生效一次；取消不产生半成品；未知结果不自动重发。

## 3. 功能要求

### 3.1 交互与代理

- **IMG-R01 · 本地交互。** 所有交互编辑在客户端完成；Server 不提供逐滑杆 RPC、帧流或会话级交互缓存。
- **IMG-R02 · 代理分层。** 区分 `displayProxy`、`editProxy`、`linearProxy`、原件；显示代理不得作为颜色敏感编辑的唯一输入。
- **IMG-R03 · 高质量 editProxy。** 默认目标为原生或高分辨率、10-bit 广色域、高质量 AVIF/HEIF；具体分辨率／位深／编码由代理契约冻结。颜色、几何、方向、蒙版坐标必须与原件一致。
- **IMG-R04 · 视口渲染。** 拖动时按视口分辨率；松手后按 editProxy 分辨率；1:1、最终、导出使用原件。不能每帧全分辨率渲染。
- **IMG-R05 · 后台预取。** 选中／进入编辑前按优先级取回 editProxy 或原件；先用 displayProxy 占位；替换不闪烁、不改变上下文。
- **IMG-R06 · 本地缓存。** editProxy／linearProxy 本地缓存，支持 LRU、TTL、固定、离线、校验；缓存键含源、解码器、profile、方向、分辨率、编码和算子版本。
- **IMG-R07 · 无 Server 图像能力。** 客户端取回原件后本地生成 editProxy／linearProxy；不能把 Server 图像模块当作编辑前置条件。
- **IMG-R08 · 色彩一致。** editProxy 使用与最终相同的色彩管理；代理分辨率可以降低，但颜色／几何语义不得改变。
- **IMG-R09 · 1:1 与最终。** 1:1、最终、导出必须使用原件；代理只作交互预览，不能冒充最终像素。

### 3.2 Server 图像能力

- **IMG-R10 · 硬件准入。** `image_module` 需要兼容 CUDA 的 NVIDIA GPU、最低显存／驱动、Vulkan 后端和 feature flag；缺一项则禁用并说明。
- **IMG-R11 · Vulkan 影像。** Linux 影像渲染和计算优先使用 Vulkan；`rawmaster-image` 是共享算子层；CUDA 后端只在单独评估后引入。
- **IMG-R12 · 生成式 CUDA。** Flux 等生成式模型使用 CUDA AI 推理栈；`rawmaster-image` 负责前置解码、色彩、蒙版、合成和后处理。
- **IMG-R13 · 能力清单。** Server 提供 `library_core`、`image_proxy`、`image_batch`、`generative`、后端、显存、引擎／模型版本；客户端按能力显示入口。
- **IMG-R14 · 资料库基线。** 无 GPU 的 Server 仍提供归档、取回、元数据备份恢复；图像模块关闭不影响资料库。
- **IMG-R15 · 资源隔离。** 资料库 RPC／归档优先；图像批处理和生成式队列有独立 GPU／显存／并发配额，不能饿死基础服务。
- **IMG-R16 · 版本绑定。** 每个作业记录 `rawmaster-image`、Vulkan／CPU 后端、RAW 解码器、色彩 profile、模型和资源摘要；缺依赖不执行。
- **IMG-R17 · 生成式模型。** 模型权重、许可、显存和输出质量独立验收；缺模型不下载、不替代、不静默换模型。

### 3.3 批处理作业

- **IMG-R18 · 作业类型。** `proxy.generate`、`render.final`、`render.batch`、`ai.heavy`、`generative`；交互编辑不是作业类型。
- **IMG-R19 · 冻结输入。** 作业冻结原件 `contentID`、配方 revision、蒙版、几何、引擎／模型、输出规格；输入变化即过期。
- **IMG-R20 · 幂等提交。** 客户端 `jobID` 稳定；Server 按 `(libraryID, jobID)` 去重；同 ID 不同请求拒绝。
- **IMG-R21 · 结果发布。** 输出先写 S3 暂存、校验、再登记派生资源／版本；同一作业只发布一次。
- **IMG-R22 · 候选采用。** 结果不自动改变当前采用版本；用户明确采用或导出；旧结果可回看。
- **IMG-R23 · 取消与重试。** 取消协作式；未发布暂存可清理；重试沿用原输入；不确定结果先核对。
- **IMG-R24 · 队列公平。** 每库配额、加权公平、优先级；一个库的大批任务不能占满所有 GPU。
- **IMG-R25 · 离线与重启。** 客户端离线保留作业镜像；Server 作业持久化；重启后恢复或转待核对。

### 3.4 队列与协同

- **IMG-R26 · 客户端背景队列。** 持久化、优先级、资源类、去重、取消、重试、离线；交互帧不进入队列。
- **IMG-R27 · Server 作业队列。** 持久化、能力匹配、租约、心跳、重试、取消、发布、过期；资料库与图像分 lane。
- **IMG-R28 · 两边不共享队列。** 客户端只保存作业镜像和本地任务；Server 是作业执行状态权威；不直连数据库。
- **IMG-R29 · 状态同步。** gRPC 提交／查询／watch；客户端按事件更新本地；重复事件幂等；断线重连补差。
- **IMG-R30 · 背压。** Server 队列满、显存不足、能力缺失返回明确错误；客户端延后或提示，不无限重试。
- **IMG-R31 · 取消传播。** 客户端取消 → Server 协作取消 → 结果不发布；Server 已完成则按核对流程处理。
- **IMG-R32 · 结果取回。** 结果通过 S3 presigned／Relay 下载；客户端校验 SHA-256 后登记候选；不把预览当母版。
- **IMG-R33 · 可见性。** 用户能看到本地任务和 Server 作业的队列、运行、失败、待核对；不伪造 ETA。

### 3.5 色彩与验收

- **IMG-R34 · 色彩门。** Server final／batch 必须消费独立色彩管理规格；未过门前只作候选／诊断，不自动采用。
- **IMG-R35 · 跨后端容差。** CPU／Vulkan／Metal 差异按色彩规格和既有 035 门槛验收；显示码值差是否允许由色彩规格冻结。
- **IMG-R36 · 生成式结果。** Flux 输出是新内容，不要求与本地同一编辑一致；仍需统一输出色彩、版本、来源和候选采用。
- **IMG-R37 · 性能基线。** 记录 editProxy 取回／生成、视口交互、final render、队列等待、结果下载、Flux 推理；注明硬件、网络、分辨率、缓存和后端。
- **IMG-R38 · 失败降级。** 缺 GPU／Vulkan／模型／色彩门时明确禁用相应队列；本地编辑和资料库继续。

## 4. 交付阶段

| 阶段 | 范围 | 可独立验收 |
| --- | --- | --- |
| Q0 · 契约 | editProxy 契约、客户端／Server 队列语义、作业 envelope、能力清单、色彩门 | 评审通过；无未决 P0 |
| Q1 · 代理无感 | displayProxy／editProxy 预取、缓存、本地生成、离线 | 进入编辑无空白；代理替换不闪烁；1:1 用原件 |
| Q2 · 客户端队列 | SQLite 背景任务、优先级、去重、取消、重试、重启恢复 | 前台交互不受影响；任务不丢；取消无半成品 |
| Q3 · Server 队列 | PostgreSQL 作业、能力匹配、Vulkan 图像 worker、租约、发布 | 五文件式作业幂等；队列公平；重启恢复 |
| Q4 · final/batch | `render.final`／`render.batch`、候选结果、色彩门 | 结果不自动采用；旧结果过期；色彩门通过 |
| Q5 · 生成式 | Flux/CUDA 队列、模型能力、结果候选 | 缺模型禁用；结果绑定；取消／重试 |

## 5. 验收场景

1. **冷片进入编辑。** displayProxy 立即显示；editProxy 后台到达；交互上下文不变；1:1 提示取回原件。
2. **Server 离线。** 本地编辑继续；客户端队列等待；重连后任务继续；无重复提交。
3. **编辑代理质量。** 原生或高分辨率、10-bit、色彩／几何与原件一致；不能把 8-bit displayProxy 当颜色敏感编辑输入。
4. **Server image_module 准入。** 无 CUDA GPU／Vulkan／feature flag 时入口隐藏或禁用；资料库仍可用。
5. **final render。** 冻结输入／配方；客户端可关闭；结果候选；不自动采用；色彩门未过只诊断。
6. **队列公平。** 一个库提交大量任务，另一个库的 short job 仍能推进；资料库 RPC 不被饿死。
7. **取消／重试。** 客户端取消传播；Server 未发布临时产物清理；重试同 ID 不重复发布。
8. **Server 重启。** 运行中作业转待核对或可续；客户端重连补差；旧 token／lease 不能发布。
9. **Flux。** 缺 CUDA／模型／显存时禁用；生成结果绑定输入／模型；不自动覆盖当前版本。
10. **色彩。** Server final 与本地最终在冻结样本和容差内一致；未过门不标“最终”。
11. **10TB／10GbE。** editProxy 预取、final、Flux、队列等待和结果下载有真实基线；不外推 100TB。

## 6. 成功标准

- **交互不被云端拖慢。** 本地滑杆／曲线／蒙版／撤销不依赖 Server；后台任务不阻塞前台帧。
- **代理高质量且无感。** 冷片进入编辑无空白；editProxy 接近原生质量；1:1／最终用原件。
- **队列不丢、不重、不脏。** 客户端重启恢复；Server 作业幂等；取消无半成品；旧结果不覆盖。
- **能力边界清楚。** 无 CUDA GPU／Vulkan／模型时明确禁用；资料库基线不受影响。
- **色彩可验收。** Server final 只在色彩门通过后作为最终；否则候选／诊断。
- **生成式独立。** Flux 队列与图像批处理隔离；模型、许可、显存和结果质量独立验收。
- **性能有基线。** 队列等待、代理、final、Flux、结果下载和资源占用可复现；不伪造 ETA 或跨环境外推。

## 7. 非目标

- Server 交互编辑、逐滑杆 RPC、帧流、会话级 GPU 缓存。
- 客户端与 Server 同一编辑请求并行渲染。
- 跨库队列共享、团队调度、多租户公平。
- 在色彩门通过前把 Server final 自动采用为当前版本。
- 无 NVIDIA CUDA GPU 时启用 Server 图像模块。
- 用 displayProxy 代替颜色敏感编辑或最终输出。
- 100 TB／200 万文件容量验收；另立专项。
