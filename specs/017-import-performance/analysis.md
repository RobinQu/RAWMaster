# 大批量导入性能分析与优化

日期：2026-10-25。范围：本地 macOS 导入、自动分组、预览风险分析和界面数据刷新。

## 为什么 CPU/GPU 使用率低仍然慢

代码显示瓶颈集中在串行等待、数据库同步提交和主线程刷新；导入不是持续 GPU 运算。整机多核使用率会掩盖单个主线程阻塞，等待文件系统/SQLite/子进程也不会产生高计算占用。

- `AppModel.receive` 原先每0.4秒同步重读整库，解码所有业务表、排序照片、重建索引并发布界面状态。每张图片的进度回调还会先建立MainActor任务，再做刷新节流。
- `LibraryStore.loadAssets` 原先每张照片查询一次membership，membership缺少以asset_id开头的索引。大量照片和分组同时存在时会反复扫描分组关系。
- `ImportService` 原先逐个发现/登记，每张照片还分别提交处理状态、结果和会话计数。SQLite保持WAL和synchronous=FULL，频繁小事务意味着频繁等待持久化。新素材discover操作还会扫描操作历史推导一个已知为0的初始revision。
- 自动分组原先逐张启动Perl/ExifTool并读取内嵌预览，启动和管道等待完全串行。前后完整SHA校验及后续质量检查还会重复读取全部原片：reference首次导入至少完整读源文件四遍。
- 质量分析虽然把解码放在后台，保存证据仍在MainActor，每12张又重读整库。
- RAW+JPEG自动关联在每次插入配对时重新解码全部既有配对，会随配对数量产生平方级开销。

当前运行应用在取样时空闲，没有捕捉到本次用户所述导入中的现场堆栈。历史`stalled-import-sample.txt`记录过目录枚举阻塞于open，但日期为10月21日，仅作历史背景。本轮结论以当前代码、隔离基准和回归为依据。

## 已实施的处理

1. 使用一次按rowid排序的membership投影，保留首个分组、顺序及任意included的既有语义；添加严格验证的可选asset_id索引。
2. 每64项发现结果共用事务；取消时提交已发现的尾批。每张文件处理结果与会话计数一起原子提交，复制、哈希和ImageIO工作不进入SQL锁。新登记操作显式使用初始revision，取消全历史扫描。
3. 导入、重分组和质量分析采用后台一致性快照；进度在进入MainActor前合并。最多一个读取在途，保留最新刷新请求，任务generation和修改epoch阻止旧快照覆盖新数据；结束前等待最终快照。
4. 质量证据写入移至后台。照片选择、搜索、派生缓存和状态发布仍由MainActor管理。
5. 元数据和内嵌预览使用2–4个worker，每小批结束后按输入顺序合并和检查预算。前后完整哈希仍顺序执行，避免放大磁盘争用。失败/取消传播到全部worker，返回前等待退出；进程隔离描述符防止并行子进程相互拖延EOF。
6. 自动配对改为在现有事务和已配对集合内直接插入，保留配对条件、已解除记录、人工配对和逐对workflow revision语义。

具体测量、回归、交付与限制见[validation.md](validation.md)。


## 真实会话追加发现

随后在用户当前727张、52GB RAW会话复测，确认长同步读取循环中的Foundation临时缓冲没有逐块释放，造成89GB级内存压力；前轮小样本未覆盖这一问题。现已逐块释放哈希/复制缓冲，并停止分组期间重复发布整库照片快照。已安装到实际运行应用并完成同批接入、分组及预览风险检查中的点击和滚动验证，详见[现场跟进验证](live-session-validation.md)。
