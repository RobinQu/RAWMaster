# 本地数据库与未来同步：SQLite / Turso 评估

> 实施进展（2026-10-21）：用户已授权实现 M1 客户端；最新状态与实际证据见 [M1 验收记录](../../specs/001-local-culling/validation.md)。以下“本次仅规划”等文字描述该文档最初的研究轮次。

日期：2026-10-21；状态：研究结论与选型建议 / 待决策，未实现或跑分。

2026-10-23 当前进展：M1 已使用系统 SQLite，Automerge 只做独立冲突保存/恢复实验，未接入运行时。本页以下仍是最初研究记录；下一批延用 SQLite，补版本迁移与领域记录，不以实现外观/分组为由换库或实现同步。见 [下一批方案](09-next-batch-review.md)。

## 1. 建议与适用前提

M1 暂以标准 SQLite 为默认候选，Turso Database 为重点对照方案。同步架构需在 M1 技术计划中提前明确；不是等 M3 才考虑，也不是因为 Turso 有同步 SDK 就立即替换数据库。

本结论针对原生 Swift Mac 客户端、离线可写、单用户多设备、x86 Ubuntu/Debian 自托管、按项目离线，以及人工决定不可被迟到状态静默覆盖的 RAWMaster。Turso 有适合这些需求的能力，但当前证据尚不足以证明整体工程成本更低。没有进行数据库、Swift 集成或同步可靠性验证，也未修改为正式获批 ADR。

## 2. 核对对象与版本

- **Turso Database**：用户链接的 Rust 数据库重写项目，与 SQLite 兼容；不是原来的 libSQL 分支。
- **libSQL**：另一套既有实现；不能把 `libsql-swift` 的成熟度或复制能力直接当作新 Turso Sync 的 Swift 支持证明。
- **Turso Sync**：建立在新引擎上的同步能力；与旧 Embedded Replicas 的默认写入路径不同。
- **Turso Cloud**：托管产品；本地引擎与仓库内同步服务器不等于必须依赖该云服务。

核对了 [v0.8.3 发布](https://github.com/tursodatabase/turso/releases/tag/v0.8.3)（2026-10-12）以及当日 `main` 提交 `a7a63042d4bfbeb38037239730ceebdc1d2c76d6`。发布、文档与主分支分别核对，不把主分支新能力默认当成所有 SDK 发布包都已具备。后续验证必须固定客户端、同步 SDK 和服务端的具体版本组合。

## 3. 适合之处与当前成本

| 维度 | 官方依据 | 对 RAWMaster 的判断 |
|---|---|---|
| 本地嵌入 | [项目 README](https://github.com/tursodatabase/turso/tree/a7a63042d4bfbeb38037239730ceebdc1d2c76d6)介绍 Rust 嵌入式引擎、SQLite 兼容、CDC、并发事务及跨平台方向；官方称已有生产用户，但尚未 1.0 | 值得验证；不因版本号判死刑，也不把生产用户表述当作本项目可靠性证明 |
| SQLite 替换范围 | [v0.8.3 COMPAT](https://github.com/tursodatabase/turso/blob/v0.8.3/COMPAT.md)仍列 SQL/C API 差异；备份 API、FTS 等需逐项核对 | 不能假定现有 Swift SQLite 包无修改替换。事务、取消、迁移、备份与诊断路径都要验证；不引用旧手册中已过时的“无索引/无触发器”等限制 |
| Swift 接入 | 当前绑定目录没有列出新引擎的专用 Swift 绑定；有 [C 兼容层](https://github.com/tursodatabase/turso/tree/a7a63042d4bfbeb38037239730ceebdc1d2c76d6/bindings/c)及 [sync C 接口](https://github.com/tursodatabase/turso/blob/a7a63042d4bfbeb38037239730ceebdc1d2c76d6/sync/sdk-kit/turso_sync.h) | 存在桥接路径，不能说 Swift 无法使用；但异步生命周期、网络 I/O、取消、打包和错误传播的成本尚未证明可接受 |
| 可选性能能力 | 并发写/异步和 CDC 有潜在价值；[SQLite WAL](https://www.sqlite.org/wal.html)也支持读写并行，仍只有一个 writer | M1 先考虑批量短事务和写入协调。RAW 解码、预览缓存可能才是主要成本；没有工作负载测量，不宣称任一引擎更快 |
| 成熟与故障恢复 | [SQLite 测试说明](https://www.sqlite.org/testing.html)涵盖崩溃、掉电、I/O 和内存异常 | SQLite 作为原片目录与人工决定存储的保守候选更有依据；本项目仍需自己的恢复测试 |

Turso 的吸引力主要是未来同步和变更跟踪，而非当前 M1 已证明的性能收益。向量搜索不应主导首版选型：基础目录与人工选片不依赖它，未来检索索引可单独演进。

## 4. 使用 Turso 后，同步仍然存在

[官方同步介绍](https://turso.tech/blog/introducing-databases-anywhere-with-turso-sync)描述本地离线变更推送与远端更新拉取，并提供自定义变更转换机制。默认冲突策略为行级 Last-Push-Wins，不按用户离线操作发生的先后决定。

例如：Mac A 离线将照片设为保留，Mac B 基于旧状态设为排除，B 最后推送。数据库可以正确执行默认收敛策略，却不符合 RAWMaster 保留决定来源、显式处理并发冲突的需求。引擎内 MVCC 解决事务并发，也不等同于跨设备离线冲突的业务合并。

因此 Turso 可以减少同步传输与变化跟踪的实现量，但仍需定义人工决定与机器建议分离、同字段冲突、组成员变化、编辑版本分支、删除/恢复，以及重试后的副作用。自定义 hook 是可用机制，不能据此宣称这些规则自动完成。

## 5. 需要分开的数据

| 数据 | 后续怎样交换 | 为什么不直接复制整个本地状态 |
|---|---|---|
| 资产/项目身份、人工评分/决定、组关系、编辑版本 | 双向交换业务变化或使用经过约束的同步记录 | Mac 与服务器都可产生有效变化；并发须保留语义 |
| 分析结果、派生输出登记 | 按输入/引擎版本发布，选择性下发 | 机器结果不能覆盖人工决定；不是每端都需要全部结果 |
| RAW、JPEG、预览与派生文件 | 独立内容传输，校验、断点恢复和按项目取回 | 数据库同步不负责 TB 级媒体传输或独立备份 |
| 本机绝对路径、挂载信息、窗口/浏览位置、缓存状态 | 设备私有或按设备登记 | Mac 路径不能成为服务器的有效路径；缓存不应全局复制 |

即使只先使用一台 Mac，服务端承担备份、处理和检索后，也要交换文件、任务与结果。只有把客户端降为全程联网的远程界面才可避免离线写入同步，这不符合已确认的产品方向。

## 6. Turso Sync 的三项重要边界

1. **自托管有基础，但运维需验证。** [官方指南](https://turso.tech/blog/building-local-first-apps-the-complete-guide-to-offline-first-database-sync)给出本地 sync server 入口，[v0.8.3 服务端源码](https://github.com/tursodatabase/turso/blob/v0.8.3/cli/sync_server.rs)也可核对。因此不能称其仅支持 Turso Cloud。反过来，这尚不能证明适合作为 RAWMaster 长期自托管服务；需要验证认证/传输保护、并发任务写入、崩溃恢复、升级与备份恢复。
2. **部分同步需要区分含义。** 官方指南称默认全库引导、部分同步为实验能力。按需取得数据库页并不自动等于按“项目”固定离线内容：必须另验项目依赖是否齐全、脱网查询行为、缓存回收和全局索引。按库拆分是候选设计，但会影响跨库检索及跨库关系，不作为已定结论。
3. **同步文件有专属访问约束。** [官方维护的同步参考](https://github.com/tursodatabase/agent-skills/blob/main/skills/turso-db/references/sync.md)强调通过同步 SDK 访问已同步数据库，并由应用安排 push/pull/checkpoint；不能将通用 SQLite 工具或非同步连接直接用于该活动文件。多进程分析任务应经数据服务发布结果，而非各自随意写同一同步文件。

第三项是 Turso 产品使用约束，不是给当前 Codex 任务增加权限要求。本次未访问或创建任何运行数据库。

## 7. 两条可行架构及选型影响

| 路线 | 本地 / 服务端 | 获得什么 | 承担什么 |
|---|---|---|---|
| A：业务级同步，当前优先建议 | Mac SQLite；服务端通过 API 接收操作，数据库可再选 SQLite 或 PostgreSQL | 按项目范围、冲突规则、计算任务与索引边界可自行定义；两端无需同引擎/同表结构 | 需要自行实现或采用合适组件完成可靠传输、去重、游标、冲突与恢复；不是零成本 |
| B：Turso Sync 作为同步基础 | Mac Turso + 同步 SDK；远端为兼容其协议/存储的服务 | 复用变化跟踪和推拉同步，可能显著减少底层工作 | Swift 桥接、自托管可靠性、作用域/部分离线和业务冲突仍要解决；遵循访问约束 |

B 不等于“本地 Turso 直接复制到任意 PostgreSQL”。Turso 的实验性 Postgres 前端也不是把数据同步到真实 PostgreSQL 的连接器。若 B 中需要 PostgreSQL 搜索/分析索引，可作为派生读模型重建；不能引入两个都能任意修改同一业务事实的主库。

无论路线，活动目录数据库都不放 SMB/NFS 让多设备共写；内容存储和数据库存储边界保持清晰。

## 8. M1 现在应该预留什么

本节为技术计划建议，尚非已批准字段或已实现代码：

- 资产、项目、组和编辑版本使用稳定的全局身份；本地递增行号不能充当跨设备唯一业务身份。
- 人工决定、机器建议、原片保留和具体序列参与分开存储；设备位置与内容身份分开。
- 用户决定持久化时，在同一事务内记录可追溯业务变更：操作身份、来源设备、目标实体、基准版本、动作内容及载荷版本。M1 用于撤销/审计，M3 可用作待发送变化；不因此要求首版实现完整事件溯源系统。
- 同字段并发不只靠时间戳或最后推送裁决；保留修订/前置版本及冲突来源。撤销产生新的可追溯变化。
- 删除意图保留可同步的标记与版本；先不物理清除同步历史，清理需考虑离线设备回归及恢复策略。
- 应用业务变更与接收确认分离，重试可去重；未来收到远端变化不能再次生成循环上传的同一变化。
- 数据模型及交换载荷都带版本，明确旧客户端升级规则。媒体文件传输独立于元数据事务，不跨数据库/文件系统虚构原子提交。

这些约定比“两个平台是否使用同款数据库”更影响未来改造成本。但不能承诺未来换引擎仅是换驱动：SQL、绑定、备份、全文索引及同步访问模型都可能需要迁移。

## 9. 决策门与后续验证（尚未执行）

M1 正式技术计划冻结前，先确定本地私有状态/共享业务状态/媒体内容三种边界，以及首版变更记录契约。Turso 若要提升为首选，须在获准实现验证时通过：

1. 固定版本组合的原生 Swift 本地读取、批量写入、取消、退出和恢复；不能仅凭 C API 兼容口号假定现有包装库可用。
2. 断网首次创建新项目、两端独立编辑再连接，以及将已有 M1 本地资料并入已有远端库；先保护未推送变化，不能通过重新引导丢失本地决定。
3. x86 Ubuntu/Debian 自托管同步服务的生命周期、认证、并发分析、升级、备份和恢复，不依赖托管云才能通过。
4. 同字段冲突、人工决定与机器结果、序列参与、删除/恢复、重复请求等故障矩阵。
5. 按项目完整离线、跨库检索及部分同步边界；若依赖实验功能，明确失败退路。
6. 代表性目录规模、导入写入与前台检索并发、批量撤销、空间回收和资源成本对照。没有测量前不引用通用跑分证明 RAWMaster 收益。

上述检查若证明 B 的可靠性与总体成本优于 A，可在 M1 数据访问层大量实现前调整选型。若暂无法完成，保留 SQLite 默认候选并按 A 规划，不把“未来可随便换”为延期同步设计的理由。

本次仅研究官方资料并更新规划；未安装数据库、未运行验证代码、未启动同步服务，也没有改变原有选型为获批状态。
