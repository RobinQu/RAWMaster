## 1. 项目目标与本轮边界

为大量 RAW 拍摄建立连续工作流：导入时即可浏览和筛选，按连拍、延时、星空等用途组织素材；Mac 可独立离线工作，联网后与自托管服务器协同完成分析、归档和备份；逐步接入历史 Lightroom 库，最后补足显影和专业序列计算。

优先减少两类成本：每次数万张拍摄的人工审阅成本，以及跨设备、跨历史资料库查找和保管素材的成本。

本轮恢复并校订四份既有草案，补充协同工作流程、参考资料与仓库阅读入口，不创建应用、服务、测试工程、数据库或运行脚本；不安装 Spec Kit，不修改 `.git`，不创建分支、提交、推送或 Issue。

## 4. 在 RAWMaster 中采用 SDD 的方式

官方核心顺序为：项目原则 → 特性规格 → 技术计划 → 任务 → 实现 → 收敛检查。澄清、需求质量清单和跨文档一致性分析是可增加的质量环节。本项目因涉及原片保管、离线冲突与异构处理，建议每个正式特性都使用这些环节。

| 阶段 | RAWMaster 产物 | 本轮状态 |
|---|---|---|
| Constitution | 项目原则及变更规则 | 仅起草，见 01 |
| Specify | 用户故事、功能要求、实体、边界和可测量结果 | 特性级提纲，见 02；尚非逐特性最终 `spec.md` |
| Clarify | 将关键歧义及用户答复写回规格 | 已写回五项确认；剩余技术问题及资料缺口见 03 |
| Plan | 技术方案、研究记录、数据模型与必要接口契约 | 仅研发路径及架构候选，不冒充已验证方案 |
| Checklist | 规格是否清楚、完整、一致的审阅清单 | 本包记录用户明确确认；样本/硬件实际到位另行记录 |
| Tasks | 按用户故事组织、有依赖顺序的实施任务 | 确认相应规格和计划后再生成 |
| Analyze | 检查规格、计划、任务之间的覆盖与冲突 | 本轮仅人工文档一致性检查，未运行 Spec Kit 命令 |
| Implement / Converge | 实现、验证并补齐差距 | 当前不进入 |

命令名称在官方资料中常写作 `/speckit.*`；Codex 等集成可能使用 `$speckit-*`。本包使用阶段名称描述流程，不假定工具已经安装或命令可调用。

## 6. 授权与变更

1. 现在只审阅和修改规划文档。
2. 用户确认规划与路径后，逐特性完善规格、技术计划和任务。批准文档本身不等于要求立即实现全部十个特性；开始范围以用户当次授权为准。
3. 规格变更先记录原因及对依赖、验收和数据兼容性的影响，再更新方案与任务。
4. 项目原则的例外必须有明确理由及替代保障，不能通过默默更改实现绕过原则。
