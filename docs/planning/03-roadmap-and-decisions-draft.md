## 2. 每个正式特性的 SDD 小循环

1. **Specify**：仅取当前里程碑需要的故事，补足边界、要求 ID、可观察结果；不一次冻结十个完整大规格。
2. **Clarify**：解决影响该特性的关键歧义，答复写回规格。需要验证的问题写明样本、判据与失败后的替代路径。
3. **Plan**：依据实际验证结果选择架构与依赖，记录研究、数据模型和必要通信契约；按项目原则审查。
4. **Checklist**：审阅规格是否完整、清楚、一致；人工审阅状态不能被实现过程自动勾选。
5. **Tasks**：按用户故事拆解，可独立演示；原片完整性、恢复、同步、迁移等风险测试列入相应故事。具体路径确定后再生成，不在本轮伪造实施任务。
6. **Analyze**：检查“要求→方案→任务→验收”覆盖与冲突，有缺口回到原阶段修正。
7. **Implement / Converge**：仅在用户授权的实现范围内执行；通过真实样本、故障及性能验收后再进入下一增量。

本项目增加的审阅/批准边界是对用户要求的落实，不意味着官方每个阶段都强制需要用户确认。规划和研发路径的方向确认已于 2026-10-21 收到；本次处理确认与基线登记，未开始原型代码、插件代码或应用工程。

## 4. 候选架构及职责

以下延续此前讨论并供评审，不是已验证的选型结论。

| 边界 | 建议职责 | 需要确定的事项 |
|---|---|---|
| Mac 原生界面 | 渐进导入、组浏览、比较、决定、离线反馈、编辑交互 | 已确认仅 Apple M4 及以后机型；本机 M4 Max/128GB；最低 macOS、SwiftUI/AppKit 分工和显示性能待定 |
| 本地目录/缓存 | 当前同步范围、操作记录、预览、离线原片和恢复状态 | SQLite 是候选；索引、迁移、事务与缓存淘汰边界 |
| 本地处理进程 | RAW 解码与分析，后续显影及序列任务；前台请求优先 | 进程隔离、常驻调用、取消与版本依赖 |
| 服务端 API/索引 | 项目/资产汇总、变更同步、任务入口、权限和副本登记 | PostgreSQL 是候选；服务端语言、部署包与认证方式待选 |
| 内容存储/备份 | 不可变原片、派生输出、暂存和完整性检查 | ZFS 或现有 NAS 能力；独立备份目标、恢复覆盖 |
| 服务端处理进程 | 原片到达后做深度分析和长任务 | 已确认 x86 Ubuntu/Debian，使用 SMB/NFS 存储；具体 CPU/GPU、内存、版本和主引擎可运行性待核实 |

资料库不是物理路径。内容 hash 不是业务身份。客户端本地状态与服务器状态通过操作/对象契约同步；原片通过单独的内容传输契约处理。

客户端可以先从源展示预览，原片暂存与校验后台推进；上传优先级依据用户决定及序列完整性。服务器需要拿到相应数据才能做对应分析，不把只接收缩略图的结果标为 RAW 复核。

首版采用明确的本地与服务端队列；任务绑定输入版本，重复提交幂等，旧结果可识别。GPU、内存、磁盘与网络都要设置资源预算。是否进一步拆服务由测量决定。

## 6. 成功标准与测量口径

### 6.1 不随硬件改变的正确性要求

- 导入/分析/迁移期间源原片字节零改写；内容校验失败不登记为完整副本。
- 恢复、重试、同步不静默丢失已确认的人工决定；并发冲突可追溯。
- 通用选片操作不隐式破坏必要序列成员；未知格式不记为摄影坏片。
- 历史迁移中未支持/缺失项目均进入报告；“未转换”不冒充“可编辑”。

这些要求在规定测试与样本中必须通过；样本测试不能被表述为已证明所有未来输入都零错误。

### 6.2 候选性能目标（全部待基线确认）

| 指标 | 建议起点 | 测量约束 |
|---|---|---|
| 首批预览可用 | 支持样本中 p95 ≤ 2 秒 | 从用户开始到首个可交互预览；允许尚未扫完整批，记录源设备与缓存 |
| 已缓存翻片/切组 | p95 ≤ 100 ms | 区分交互响应与高分辨率细节就绪；后台复制/分析同时运行 |
| 首次 RAW 细节就绪 | 本地原片样本 p95 ≤ 2 秒 | 100% 指实际细节来源；按机型/压缩/分辨率分别报告，不混用内嵌 JPEG |
| 元数据跨库检索 | 热缓存 p95 ≤ 500 ms，冷缓存单列 | 查询集合、结果上限、资产规模固定；不含语义搜索 |
| 人工审阅耗时 | 同等素材相对个人基线减少 ≥ 30% | 同等选择完整性；按每万张标准化，注明初次使用学习成本 |
| 大批导入 | 3 万张作为候选一轮压力负载 | 同时报告吞吐、峰值内存、首图与细节延迟，不能只测最终完成速度 |

不在未知硬件上承诺以上数值；若 V1/V4 表明不可行，调整需求或架构并记录原因，不能事后改口径使数据达标。容量档位建议先真实规模，再按需求补 10 万/100 万索引；合成索引仅测目录性能，不能代替真实 RAW 读取和画质验收。

### 6.3 建议质量与误排除口径

建立人工标注集合并留出未用于调参的评估部分。按拍摄类型、机型与主体类型分层报告，不只报总平均：

| 指标 | 定义与用途 |
|---|---|
| 优秀片误排除建议率 | 人工认为应保留的照片中，被系统建议排除的比例；即使用户最终救回，也计为误排除建议 |
| 必要序列帧误排除率 | 人工认为该次处理必需的成员中，被建议移出该序列的比例；独立入选与此分开统计 |
| 自动排除率/误排除率 | 仅未来真正开启自动排除时统计；首版人工确认不能被包装成自动化安全证明 |
| 坏片检出与建议精度 | 能识别多少已标注技术失败项，以及排除建议中有多少正确；与误排除预算同时看 |
| 未知/不适用比例 | 无法稳定判断或规则不适用的比例；不把未知排出分母以美化整体覆盖率 |
| 人工复核成本 | 每组/每万张耗时、纠正次数、证据打开次数，和不使用建议时的个人基线比较 |

自动排除的可接受阈值暂不替用户确定。未来即使评估样本中未出现误排除，也需说明样本量和不确定性，不能宣称错误率必为零。

## 12. 后续自动排除增量（F003.US4）

这是 2026-10-21 新增的明确用户要求。M1/M2 首次交付继续采用人工确认；自动排除作为 M2 之后的独立增量，不改变已确认 M1→M5 主线，也不要求等待完整显影。具体发布批次由 V2 与用途保护验证结果确定，不无期限留作可选设想。

依赖 F002 决定/撤销、F003 有效质量分析、F004 用途/序列保护；远端自动执行还需相关归档与同步能力。研发顺序：建立代表性标注与留出评估集 → 只记录结果的影子评估 → 冻结分类型误排除预算/覆盖指标及停止条件 → 按项目显式启用 → 验收原因追踪、暂停、批量撤销与重连恢复。

首个支持范围在验证后选择，候选为失焦或异常曝光等可解释技术失败项。未知用途、受保护序列/校准帧、解码失败及人工已确认保留项不自动排除；相似度不能单独决定排除。自动排除只改变可恢复的独立入选状态，不负责物理删除。阈值尚未确定，不能宣称已达到安全启用条件。
